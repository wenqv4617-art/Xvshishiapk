## v2 核心变化：总结也按真实时间线

v1 为了保住 `summaries.endRound` 的轮次索引语义，自动总结里把线下记录"追加在线上之后"。但你要求的是**线上/线下任意来回切换、记忆互通、总结也按时间线**——如果线下赴约发生在线上聊天中间（线上10轮 → 赴约 → 线上继续聊），时间线穿插会让轮次索引漂移，导致线上记录漏总结。

**v2 方案：把总结进度追踪从"轮次索引"改为"消息级标记"**

| 内容 | 进度标记 | 含义 |
|------|---------|------|
| 线上消息 | `messages.summarized = 1` | 已被总结，不再参与后续统计/拼入 |
| 线下赴约记录 | `offline_messages.mergedArchived = 1` | 已跟随线上总结自动存档 |

- 合并列表 = 线上**未总结**消息 + 线下**未存档**赴约记录，**按时间戳严格排序**（线上线下同一算法 `buildRoundsFromStream`）
- 进度判定只看消息级标记，与"它在列表里的位置"无关 → **任意穿插、多次切换都不会漏总结或重复总结**
- 总结成功后，把该区间内的线上消息标 `summarized=1`、线下记录标 `mergedArchived=1`
- 记忆面板统计 / 手动总结默认区间也基于同一套标记，口径一致

## 三、核心设计决策（v2）

1. **消息级进度标记替代轮次索引**：`messages.summarized` + `offline_messages.mergedArchived` 是唯一进度依据，彻底消除"列表重建导致索引漂移"的问题。这是 v1 → v2 的关键升级。
2. **单次自动总结上限 100 轮**：老数据/长期积压时防止一次总结 token 爆炸；未覆盖部分在后续触发中继续消化。
3. **兼容性**：老会话线上消息无 `summarized` 标记，首次自动总结会把历史消息重新总结一遍（一次性成本，之后正常）；`summaries.startRound/endRound` 语义变为"总结时的待总结列表区间"，仅用于排序展示与检索去重（去重不精确只影响 token 冗余，不影响正确性）。
4. **向量轮次隔离不变**：线下 roundIndex 负数（-1,-2,...），升序后天然作为历史参与检索。
5. **开关字段不加 db.js schema**：避免数据库版本迁移。
